# 翻译模型渠道对比与 gpt-5.6-luna 思考/缓存实测

日期：2026-09-09（周三，非直播日实测 + 晚间直播流验证）

## 决策

翻译模型从 `go/deepseek-v4-flash` 切换尝试 `gpt-5.6-luna`（CPA 渠道），实测后**暂定 `dss/deepseek-v4-flash` 试用一阵**。gpt-5.6-luna 保留为备选，回切前需先解决缓存与思考问题（见下文研究结论）。

## 渠道实测对比（生产直播流数据）

| 指标 | gpt-5.6-luna（CPA 渠道） | dss/deepseek-v4-flash |
|---|---|---|
| 延迟 | 2.8~10s，多数 3~5s | **1.2~2.4s**，均值 ~1.5s |
| 思考 tokens | 15~134/次（禁不掉） | **null**（非思考模型，字段不存在） |
| 前缀缓存 | 命中不稳定，经常 read:null 全量重算（in≈4000） | **头 2 条 miss 后 100% 命中**，增量 in 仅 33~157 |
| 缓存可观测 | read 有值、create 恒 null | read/create 都有 |

## gpt-5.6-luna 三个坑

### 1. 思考禁不掉（当前调用方式下）

代码走 `/v1/messages`（Anthropic 端点）+ `thinking:{"type":"disabled"}`——这套对 go/（ollama pro 思考模型）有效，**对 CPA 渠道无效**：转换链丢弃该参数，模型始终以默认档位思考 15~134 tokens/次。实测全部无效的写法：`reasoning_effort`（minimal/none）、`reasoning:{"effort":...}`、`thinking:{"type":"enabled","budget_tokens":128}`——thinking_tokens 全在 14~38 噪声带。

- 功能上无害：返回的 thinking block 内容为空，`aiQuery` 的 `filter(b.type==="text")` 天然过滤；仅轻微延迟
- 彻底关闭需切 `/v1/chat/completions` 端点：**实测该通道默认零思考（连参数都不用传）**，但需改端点、body 格式、响应解析、usage 字段，非只换模型名

### 2. 缓存命中不稳

prompt 前缀设计已是严格递增（共享对话流），命不稳的根因在渠道侧：GPT-5.6 起隐式缓存匹配不可靠（Azure 上有同类报告：5.6 恒 cached_tokens:0、5.5 正常），需 `prompt_cache_key` 路由稳定。

### 3. 延迟与思考正相关

最差样本 `in=4022, think=116, read=null` → 9.96s（全 miss + 高思考叠加）。担心"提示词变长思考暴涨"实测未发生：in≈4000 时 think 在 23~116，与短输入基线同量级。

## 若回切 gpt-5.6-luna：缓存优化路径（已研究未实施）

**`prompt_cache_key` 是 body 参数不是 header**（OpenAI GPT-5.6 起官方定位为 reliable matching 的必要参数）。机制：路由按「前 ~256 tokens 哈希 + key」固定实例；单 key 上限 ~15 RPM，超出溢出到冷实例。

CPA（router-for-me/CLIProxyAPI）源码机制（GitHub 源码级确认）：

- `sdk/cliproxy/session/info.go`：session 识别优先级第 10 位是 `prompt_cache_key`（pck: 前缀），顶层或嵌套均可识别，与入口格式无关
- `sdk/cliproxy/auth/selector.go`：凭证选择按 session 亲和——**同一 pck 粘同一上游账号**，这是命中稳定的主因（账号池轮换 = 缓存各自为政）
- `internal/runtime/executor/codex_executor_request.go`：OpenAI/Responses 入口的 pck 直接透传上游并写 `Session-Id` 头；`server_routes.go` 的 delete 只针对 Codex Alpha Search 专用净化，通用路径不删
- `config_types.go`：`support-prompt-cache-key` 配置项控制"派生 key 注入"，部署侧需确认是否开启（CPA 部署在别处，未核实）
- `helps/claude_code_session.go`：识别为 Claude Code 请求（需其专属 session header）会自动派生确定性 key——我们不是 Claude Code 特征，走不了这条

其他约束：显式缓存（`prompt_cache_breakpoint` / `prompt_cache_options.ttl:"30m"`）仅 Responses API 支持；缓存写入计费 1.25×、读取 0.1×。

**未验证**：`prompt_cache_key` 在 `/v1/messages` Anthropic 格式下能否穿透 new-api → CPA 双层转换到达上游（源码看 session 亲和层应该能识别，但没实测）。

## 观测手段

`ai.ts` 的 `[usage]` 日志已加 `think` 字段（`usage.output_tokens_details.thinking_tokens`）。注意 `out` 是总量（out = think + 正文）。看日志：`ssh mini "docker logs -f livetrans 2>&1 | grep --line-buffered usage"`。dss 渠道无此字段（think:null 属正常，非字段丢失）。
