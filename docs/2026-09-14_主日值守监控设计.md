# 主日值守监控设计（mini 侧监控 + 转录检查端口）

> 2026-09-14 定稿（v2 架构）。需求：每周主日（周日）07:40-09:25，开始时间检查 stream 音频输入与字幕链路，结束时间检查是否仍在直播，异常时通知管理员。

## 最终架构

```
mini (livetrans 容器, server/plugins/monitor.ts)
  │ 定时 tick (默认20s), 主日窗口内排程开始/结束两个检查点
  │
  ├──拉取──▶ home 转录 /status 检查端口 (run_client.py :9091)   ← 单一外部数据源
  │           返回: 流三态(ok/silent/no_stream) + 峰值dB + 包计数
  │                    + WS状态 + ASR最近字幕时间 + uptime
  ├──读本进程──▶ pipelineStatus (listen.ts 埋点, 同进程内存)      ← 字幕口径
  │           lastAt / lastCurrentAt / lastConfirmedAt
  └──异常──▶ tellme webhook (n8n, 与 report.ts 同通道)
```

**监控放 mini 的核心逻辑**：转录服务（home）本身就是被检对象——转录挂掉 = `/status` 拉取失败，天然可检，无需任何额外探测通道。mini 侧一次拉取即拿全"转录可达性 + 音频三态"，字幕流水又本来就在 mini 进程里。

**值守是一次性通知**（用户定版哲学）：任意环节出问题报告管理员后即由人跟进，不做多源二次诊断——转录不可达时不另行探测 SRS 推流，消息如实标注"无法探测"即可。

## 检查点语义

### 开始检查（07:40 + 宽限180s 后允许告警）
三个状态，任一异常即告警，消息携带全部状态：

```
[livetrans 值守] 2026-09-20 07:44:31
⚠️ 主日礼拜已开始（07:40），检查异常且持续 60s 未恢复：
· 转录服务 ✅ 可达（uptime 1594s）
· 音频源 ❌ 无流
· 字幕 ❌ 最近 30 分钟未收到任何字幕（最近 07:12，正式 07:12）
```

- 转录服务：`/status` 拉取成功（超时 5s 判失败）
- 音频源：`stream.state` 三态——`no_stream`（最近 10s 无数据包）/ `silent`（30s 滑窗峰值 ≤ -60dB，数字静音 -91dB，调音台静音在 -60~-90 区间）/ `ok`；转录不可达时为 `❓ 未知`
- 字幕：**最近 30 分钟**（`MONITOR_SUBS_LOOKBACK_SEC`，滚动窗口，用户定版口径）内 `lastAt` 有过 listen 流量（含 current 预览）

### 结束检查（09:25 + 宽限120s 后）
- `/status` 可达且 `stream.state ∈ {ok, silent}` → 通知"仍在直播，请确认是否停止推流"
- `no_stream` → 已停播，不打扰
- 转录不可达 → 无法判断直播状态，**不重复通知**（开始检查已报过，管理员处理中）

### 防误报两级机制
1. **宽限期**：开始检查推迟到开始时间+180s 才允许告警（等推流/开声就位），宽限期内只打日志
2. **二次确认**：异常持续 60s 不恢复才真通知，期间恢复则静默通过；当天每检查点只通知一次（内存态去重，跨天失效）

### 边界行为
- **周日限定**：默认 `MONITOR_SERVICE_DAYS=sun`，非主日整天不检查（避免非礼拜日 7:40 的日常误报）
- **补跑**：窗口内前端容器（重）启动 → 首个 tick 立即评估；过窗口才启动则开始检查作废（事后补报无意义），结束检查照跑
- **时区**：上海时间显式 `+8` 偏移计算（`Date.parse('...T..:..+08:00')`），不依赖容器 TZ
- **dev 模式模块双实例坑**：Nitro dev 下 plugin 与 route handler 可能各持一份模块副本，`pipelineStatus` 的 state 必须挂 `globalThis`（实测踩过：dev 里 listen 埋点写了 A 副本、监控读 B 副本恒为 0；生产单 bundle 无此问题，globalThis 两端兼容）

## home 侧：转录检查端口（run_client.py）

- `GET :9091/status`（env `LIVETRANS_STATUS_PORT`，0=关闭），标准库 `ThreadingHTTPServer` 线程，高频轮询不刷日志
- 状态跟踪在 `whisper_live/client.py`：`handle_ffmpeg_process` 每收包更新 `last_stream_data_at`/包数/30s 滑窗 RMS（`_note_stream_data`）；`Client.process_segments` 记录 `last_segment_at`（诊断用）
- 转录进程挂掉端口即消失 → mini 侧判"转录服务不可达"——不隐藏故障，正是设计意图
- mini 容器 → home:9091 可达性：home WSL2 为 **mirrored 网络模式**（WSL 直接持有 LAN IP 192.168.123.16），实测容器内 fetch 直通，无 portproxy 需求

## env 配置（均有默认值，不配即主日 07:40-09:25 且真通知）

**mini 侧**（`MONITOR_*`，nuxt.config.ts runtimeConfig，`NUXT_` 前缀可运行时覆盖）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `MONITOR_ENABLED` | `1` | `0` 关闭监控 |
| `MONITOR_SERVICE_START/END` | `07:40`/`09:25` | 礼拜窗口 HH:MM（须同日且 END>START） |
| `MONITOR_SERVICE_DAYS` | `sun` | `sun,mon...` 逗号分隔或 `all` |
| `MONITOR_START_GRACE_SEC` | `180` | 开始检查告警宽限 |
| `MONITOR_END_GRACE_SEC` | `120` | 结束检查延迟（礼拜拖堂+停推流人工延迟） |
| `MONITOR_CONFIRM_SEC` | `60` | 异常二次确认时长 |
| `MONITOR_SUBS_LOOKBACK_SEC` | `1800` | 字幕"有/无"滚动回看窗口 |
| `MONITOR_CHECK_INTERVAL_SEC` | `20` | tick 间隔 |
| `MONITOR_TRANSCRIBE_API` | `http://192.168.123.16:9091/status` | 转录检查端口 |
| `MONITOR_DRY_RUN` | 空 | `1` = 只打印不发送 |

**home 侧**（`LIVETRANS_*`，client.py/run_client.py 读取）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `LIVETRANS_STATUS_PORT` | `9091` | /status 端口，0=关闭 |
| `LIVETRANS_SILENCE_DB` | `-60` | 静音判定阈值（峰值 dB） |
| `LIVETRANS_STREAM_FRESH_SEC` | `10` | 多久没收到数据包判"无流" |

## 实测记录（2026-09-14，真实推流 + 真实 tellme 通知）

用 Windows 桌面讲道音频（`2026-04-12主日上午1`，82min）经 `ffmpeg -re -ss 30:00 ... rtmp://mini:11935/live/livestream` 实际推流，home 转录客户端 2s 断流重试循环自动接上：

| 场景 | 结果 |
|---|---|
| 推流中 `/status` | `state=ok`，峰值 -6.4dB（真实讲道音频）；包计数持续增长 |
| 全绿开始检查 | 转录✅可达 音频✅ok 字幕✅有 → 正常不告警 |
| 推流中到结束点 | **真实 tellme**"已到结束时间但仍在直播（峰值 -6.5dB）" |
| kill 推流后 | `/status` 2s 内回归 `no_stream` |
| 断流+无字幕开始检查 | 宽限观察 → 二次确认 → **真实 tellme** 告警（转录✅ 音频❌无流 字幕❌） |
| 停播后到结束点 | 判已停播，不通知 |
| 转录不可达（dry-run 验证） | 告警"转录❌不可达(ECONNREFUSED) + 音频❓未知 + 字幕❌" |
| 静音/有声文件探测 | -91dB → silent；-24dB → ok |
| SRS 空闲行为 | 拉流挂连接等推流（不 404），转录侧按"无数据包"归 no_stream，语义正确 |

边界实测补充：SRS `/api/v1/streams/` 在无推流时也可能残留条目（拉流客户端挂着，`publish.active:false`）——若未来需要"查 SRS 判直播"，须看 `publish.active` 而非 streams 非空；本设计不需要（单源原则）。
