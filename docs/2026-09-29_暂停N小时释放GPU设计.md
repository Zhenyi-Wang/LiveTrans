# livetrans 暂停 N 小时释放 GPU 设计与实测

> 2026-09-29 定稿。玩游戏/跑 GPU 任务时一键暂停转录服务释放显存，到期自动恢复。

## 需求与方案概要

- **HTTP API 暂停/恢复**：挂在已有的 :9091 检查端口上，`POST /pause?hours=N` / `POST /resume`
- **暂停 = 零显存**：断 WS + 杀 run_server 进程（模型按 WS 连接加载，断连杀进程即彻底释放）+ 杀 ffmpeg；到期重建全套
- **崩溃安全**：暂停态落盘 `pause_state.json`（仓库根，gitignored）；暂停期 run_client 崩溃被 main.py 拉起后，`TranscriptionClient.__init__` 检测落盘态 → 跳过 server/WS 初始化 → **模型永不加载，显存保持零**
- **不动 main.py**：暂停完全在 run_client 进程内实现，监督循环零感知（进程不退出就不触发重启）

### 关键实现位置（client.py）

| 位置 | 作用 |
|---|---|
| `TranscriptionClient.__init__` | **暂停拦截点必须在构造函数**：`Client()` 构造即启 WS 线程、server 收连接即加载模型，等到 `__call__` 再拦就晚了 |
| `TeeClient.__init__` 空 clients 放宽 | `_paused_startup` 哨兵守卫（运行期空 clients 本就是断流后的合法态） |
| `handle_ffmpeg_process` 外层顶部 | 暂停检查点 + 幂等 teardown（WS→server→ffmpeg）→ `_wait_until_resume`（sleep 1s 轮询）→ rebuild（异常不吞，冒泡退出由 main.py 拉起自愈） |
| 内层 select 等待循环 | **等数据期间也检查 paused**（流离线但 ffmpeg 未退出的挂起态，外层检查点永远到不了——实测踩坑） |
| 断流 sleep 分片（1s 步进） | 90min 后退避到 60s 时暂停仍能 1s 生效 |

## API

| 端点 | 语义 |
|---|---|
| `POST /pause?hours=2` | 暂停 N 小时（小数支持，无参默认 2，上限 48）；**重复调用覆盖**旧 resume_at |
| `POST /resume` | 立即恢复（幂等） |
| `GET /status` | 新增顶层 `paused` / `resume_at`(epoch ms) / `resume_at_iso` |

- 参数走 query string（.bat/curl 最简）；非法值 400 + JSON 错误
- **不加鉴权**：暴露面与 /status 相同（LAN + WG 可信网络），注意 mini/LAN 内任意机器可触发
- 写序崩溃安全：pause 先落盘后置内存、resume 先删文件后置内存——任何崩溃窗口收敛到安全侧

## 实测矩阵（2026-09-29 全过）

1. 暂停 0.01h：teardown 8s 内完成，server 进程消失（exit -15），显存 4894→2915 MiB（释放 ~2G）
2. 到期自动恢复：到期 +1s 触发，server 重建 + 模型加载 6s + WS 重连，显存回升
3. 手动 resume：即时恢复；多次快速 pause/resume 循环稳定
4. 覆盖语义：pause 0.02h → pause 0.05h，resume_at 差值 = 108s（0.03h）✓
5. 参数容错：abc/0/100/-1 均 400；未知路径 404
6. **崩溃恢复（核心）**：pause 2h → pkill run_client → main.py 5s 拉起 → 日志"启动时发现落盘暂停态，剩余 2.00h" → **显存保持 2915（模型零加载）** → resume 恢复
7. 状态文件损坏：启动时"忽略并清理"，正常启动
8. Windows localhost:9091 转发可达（curl.exe 实测）
9. mini dry-run：`⏸️ 转录已暂停（预计 2026-09-29 18:12 恢复）` 完整走通告警管线

## 顺手修复的两个存量 bug

1. **`_server_process` 句柄被抹（严重）**：`TranscriptionTeeClient.__init__` 会把 `_server_command/_server_process` 重置为 None（独立使用的默认值），而 `TranscriptionClient.__init__` 先 `start_server()` 再调 TeeClient init → 句柄当场丢失 → **`stop_server()` 从此静默 no-op，断流 90min 自动释放 GPU 的老功能早已失效**（表现为：流离线一整天 server 仍挂着模型）。修复：init 后恢复句柄
2. **`MONITOR_DRY_RUN=1` 运行时失效**：Nuxt 用 destr 反序列化 env 覆盖，`=1` 变数字 `1`，原判断只认 `true/'true'/'1'`。修复：`Number(rc.monitorDryRun) === 1`。⚠️ 修复前实测曾向真实 tellme webhook 发出一条测试期误报（2026-09-29 18:08，周二窗口试探）

## 运维备忘

- 暂停状态文件：`pause_state.json`（仓库根，gitignored，含 resume_at/paused_at/hours）；手删 = 强制恢复正常
- kill-session 重启会孤儿化 run_server（SIGHUP 不触发 python 清理），下次启动 `_kill_port_users` 自动清理，D 态滞留可达分钟级，属已知现象
- `pgrep -f` 排查时用 `run_server[.]py` 防命令替换子进程自匹配
