# 缓存命中率 82% 结构分析与日志时区修复

日期：2026-09-14（分析对象：2026-09-13 周日礼拜全天）

## 一、数字对账：本地日志与 DeepSeek 平台侧完全一致

平台侧（dss 渠道账单口径）：命中 23,876,467 / 未命中 5,150,371 / 输出 223,953。

本地 `[usage]` 日志聚合（mini 容器，6841 条请求、0 错误）：

| 字段 | 汇总 | 对应平台口径 |
|---|---|---|
| `read` | 23,876,467 | 命中（分毫不差） |
| `create` | 0 | DeepSeek 不经 anthropic 层上报缓存写入（写入免费且不可观测，与 go/ 的"恒 0"不同源） |
| `in` | 5,150,371 | 未命中（分毫不差） |
| `out` | 223,953 | 输出（分毫不差） |

结论：**dss 全部流量走单一 key、本地日志 100% 覆盖、无统计口径差**；且全天 6841 条请求 read 最低 2560（= system 段），**缓存从未完全冷掉**（礼拜连续 4 小时内无超 TTL 的空窗）。

## 二、命中率 82.26% 的结构：miss 呈完美双峰

| 未命中区间 | 请求数 | 未命中量 | 占比 | 均值 | 含义 |
|---|---|---|---|---|---|
| ~200 tok | 4128 | 870,224 | 16.9% | 211 | 仅最后一条新 user 消息，理想命中 |
| 1500-1700 tok | 2658 | 4,257,430 | 82.7% | 1602 | **整条对话流窗口全量重发** |

双峰即两种稳态：同一"世代"（两次 append 之间）内的后续请求全部命中（preview 连发 + 本批 confirmed）；每个新世代的第一条请求把 ~1300 token 窗口 + ~200 user 全量重发。

## 三、根因：20 轮滚动窗口全天饱和，每批 append 都触发 shift

`messages` dump diff 实锤：相邻热/冷请求的历史分别是 `[turnA, m1..mk]` 与 `[m1..mk, turnB]`——**追加 turnB 的同时头部丢掉了 turnA**。两侧 dump 均 41 条消息 = 20 轮×2 + 当前 user，即窗口全天顶满 `HISTORY_MAX_ROUNDS=20`（.env 未覆盖默认值）。

因果链：

1. 窗口饱和 → 每批 confirmed 成功 append 一轮、`shift()` 驱逐最旧一轮 → **窗口头部每批都移动**；
2. 前缀缓存只认 append-only——头部一动，system 之后全部断裂；
3. 每个世代第一条请求全量重发窗口（miss≈1530），同代后续请求只 miss 新 user（miss≈200）；
4. 冷请求数 2658 ≈ confirmed 批次数 2182（+fallback 等边界），量上闭环；
5. `confirmed:2` 冷占比 94%：积压时 drain 背靠背、无 preview 插入保温，**每批 confirmed:2 本身就是新世代第一条**；
6. `confirmed-fallback` 天然 `history: []`（异常路径设计如此），read=2560。

礼拜日 ~2000+ 批，"偶发截断"实际是**每批连续截断**——CLAUDE.md 里"截断处前缀断裂一次全 miss 后恢复"的假设在饱和态不成立。

## 四、结论与可选优化

**82.26% 合理**：它是"有界窗口 + 前缀缓存"的结构性稳态，不是异常或浪费——重发部分是维持翻译上下文所必需的输入。

若想提升（未实施，留待决策）：

- **攒 K 批一次性驱逐**：`shift` 从"每批 1 条"改为"超限 K 条时一次驱逐 K 条"，断裂频率降为 1/K，miss 降约 (1−1/K)（K=5 → 命中率 ~95%）。代价：窗口在 40~40+K 间波动、翻译上下文轻微不均。
- **调大 `NUXT_CONFIRMED_BATCH_MAX`**：世代数减少同样降低断裂次数，代价是 confirmed 字幕延迟上升。
- 两者都以延迟/上下文质量换 token，单场节省量级约 ¥几块，优先级低。

## 五、日志时区修复（已部署）

问题：`docker logs -t` 时间戳恒为 UTC（dockerd 打点，与容器 TZ 无关），昨天的礼拜在日志里显示为"凌晨 0-4 点"。

修复（2026-09-14 经 `sync-mini.sh -b` 部署生效）：

- `docker-compose.yml`：environment 增加 `TZ=Asia/Shanghai`（容器内 `date` 已 CST）；
- `server/utils/ai.ts`：`[usage]` 成功/失败两路日志增加 `ts` 字段（`toLocaleString` 显式 `Asia/Shanghai`，不依赖容器 TZ），**今后分析日志以 `ts` 字段为准**，`docker logs -t` 仍会显示 UTC（记得 +8）。

## 六、落地（2026-09-14）

方案（spec/plan 见 `docs/superpowers/`，同日定稿）：

- `segments.ts` 锯齿窗口：超 `NUXT_HISTORY_MAX_ROUNDS`(默认100) 轮一次裁到 `NUXT_HISTORY_MIN_ROUNDS`(默认20) 轮，前缀断裂从每批一次降为每 ~(MAX-MIN) 批一次；裁剪时打 `[history]` 日志
- `listen.ts` 预览频率闸：距上次 LLM 发起 ≥ `NUXT_PREVIEW_MIN_INTERVAL_MS`(默认3000ms，start-to-start) 才发起下一次；最新者胜/单飞结构/previewCache 不占闸均不变

参数依据（本文件第二~四节 + 参数扫描）：断裂间隔最优 ≈20 批（命中/未命中价比 1:50 决定）；窗口尺寸经命中费线性加价，"大窗口免费"只到 ~40 轮；20/100 为用户在费用谷底上方拍板的质量选型。

模拟预测（当天数据重放）：命中率 82.26%→98.3%，¥12.97→~¥4.1（并发修正 ~¥4.7），preview 调用 4659→~3048。
