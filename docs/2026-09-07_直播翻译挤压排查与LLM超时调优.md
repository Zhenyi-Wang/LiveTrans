# 直播翻译挤压排查与 LLM 超时调优

> 2026-09-06 主日直播中出现"翻译挤压"（字幕停滞一段时间后猛补），当日完成排查与调优，文档定稿 2026-09-07。

## 现象

直播中观众端字幕出现明显积压：正式翻译（confirmed）停滞约 2-3 分钟后快速补出。

## 排查证据链

数据链路：whisper client（本机）→ POST `/backend/api/listen` → mini 前端 Nitro（翻译队列）→ LLM 网关。逐层取证：

| 层 | 证据 | 结论 |
|----|------|------|
| 后端 dispatch | POST 到达延迟 p50=0.98s、max 1.7s，无重试积压 | 正常 |
| 前端容器 | 8/30 起零重启、无 OOM，慢时段无自身报错 | 正常 |
| LLM 调用 | 07:37:37 起完成间隔拉大；**07:39:51 一次调用打满 60s 超时**（全时段唯一失败）；07:39 吞吐腰斩（23 条/分钟 vs 正常 40+） | **异常** |

07:40 上游恢复（44 条/分钟），积压约 1-2 分钟排空——对应观众看到的"猛补"。

## 根因与放大机制

**根因**：LLM 上游（`go/deepseek-v4-flash` @ ollama pro 云）07:37-07:40 响应劣化约 3 分钟，其中一次调用挂死至 60s 超时。

**放大机制**：confirmed 串行 drain + 全局并发仅 2（`ai.ts` 的 `MAX_LLM_CONCURRENT`）。一次 60s 超时把一个并发槽死占 60 秒，期间 confirmed 正式翻译**零产出**；前后慢调用（单次 3-4s → 5-10s+）使消费速率低于产出，积压形成。

## LLM 耗时实测（2026-09-06，12 分钟真实直播流量，n=252）

新增 `ms`/`ch` 日志字段后实测：

| 通道 | n | p50 | p90 | p99 | max |
|------|--:|----:|----:|----:|----:|
| confirmed | 85 | 1.4s | 1.9s | 8.5s | 8.5s |
| preview | 167 | 1.3s | 1.8s | 3.3s | 8.4s |

- \>10s 零条；>5s 仅 0.79%（两条且为同一毫秒时刻的网关瞬时抖动）
- 长尾来自偶发抖动（几秒自愈），不是常态分布的一部分

## 调优改动

1. **`[usage]` 日志增强**（commit 0be0102）：加 `ms`（耗时）与 `ch`（通道：`preview` / `confirmed:N` / `confirmed-fallback`）字段，失败路径（超时/网关错误）同样记录（`err` 字段）
2. **超时可配置并默认 15s**（commit f41f5dc）：原 60s 硬编码 → `NUXT_LLM_TIMEOUT_MS` 可覆盖，默认 15000ms。15s ≈ 1.8×p99，正常抖动零误杀；事故时最坏停摆 60s → 15s

   **钳位必须放在使用点（ai.ts）**：runtimeConfig 的 `NUXT_` 前缀运行时覆盖由框架 destr 映射直接替换烘焙值，绕过 nuxt.config.ts 里 build 时求值的钳位表达式。`AbortSignal.timeout` 在 Node 下的完整行为（三轮 review 迭代 + Node v22 实测结论）：
   - 非整数小数（如 `1500.5`）→ 同步抛 RangeError → 全部调用秒失败
   - `(2^31, 2^32]` → **不抛错**但内部 setTimeout 溢出警告、时长置 1ms → 每次调用立即超时（静默全灭）
   - 负数 / NaN / 超上限 / 字符串型（destr 解析不了的如 `"15s"` 原样传入）→ 同步 RangeError 或 NaN 透传
   - 最终收敛表达式：`Math.min(2147483647, Math.max(1000, Math.trunc(Number(config.llmTimeoutMs)) || 15000))`——上限是 setTimeout 的 32 位有符号整数边界，不是 uint32 上限 4294967295（那恰是死区）

## 观测盲点与遗留建议

1. `ai.ts` 的 `{ messages, result }` 大 dump + `listen.ts` 的 `Received data` 全量 dump 把 mini 容器 docker 日志冲成约 25 分钟滚动窗口，历史不可回溯——建议挂 DEBUG 开关
2. 超时误杀的成本是重试 1-2 次（1s 间隔），字幕多抖一下；不建议阈值低于 10s（p90→p99 之间有真实长尾，截太狠会放大重试流量）
3. 本次排查只能靠间接证据（完成间隔）重建延迟，`ms` 字段上线后此类分析可直接进行
